# collab-session-wrap — 세션 마무리

```
① 세션 훑기 → ② 볼트 갱신 → ③ 메모리 갱신 → ④ **스킬 갱신** → ⑤ 보고 + "이제 /compact 하세요"
```

⚠️ **`/compact`는 스킬이 못 누른다.** ①~④를 **끝까지** 해두고 마지막에 대표가 한 번 누른다.
그러니 ⑤ 보고 없이 끝내지 마라 — 대표는 그 보고를 보고 컴팩트해도 되는지 판단한다.

⛔ **이 작업은 서브에이전트에 위임하지 마라**([[delegate-by-default]]의 명시 예외).
무엇이 결정이고 무엇이 잡담이었는지, 어떤 판정이 뒤집혔는지는 **이 세션의 대화에만** 있다.
서브에이전트는 git log와 파일만 보므로 **결정의 '왜'를 통째로 잃는다.**

## ① 세션 훑기

먼저 **무엇을 남길지** 정한다. 코드가 이미 말하는 건 남기지 않는다.

```bash
git log --oneline -30            # 이 세션 커밋
git log -1 --format=%H -- <볼트에 마지막으로 적힌 커밋>   # 어디까지 기록됐나
```

**남길 값이 있는 것** (이 중 해당되는 것만):
- **결정과 그 근거** — 특히 *왜 다른 선택지를 버렸는가*. 이게 없으면 다음 사람이 같은 걸 또 제안한다.
- **뒤집힌 판정** — "확정했다가 다시 보니 아니었다"는 그 자체가 데이터다.
- **사고와 재발 방지** — 무엇이 깨졌고, 순서·전제 중 무엇이 틀렸나.
- **실측으로 정정된 통념** — 문서·메모리에 틀리게 적혀 있던 것.
- **대표가 판단해야 남은 것** — 미결 질문.

**남기지 않는 것**: 코드 구조, 커밋 메시지에 이미 있는 사실, 이 세션에서만 쓰는 임시 정보.

### ⭐ 현재 상태 문서 vs 역사 기록 — 다르게 다룬다

- **현재 상태를 말하는 문서**(제품-정책서·DB-스키마·인프라-운영·스킬) → **내용을 고친다.** 낡은 문장을 남기면 다음 사람이 그걸 믿는다.
- **그때의 결정을 남긴 기록**(의사결정-로그·완료된 `1_Projects` 노트) → **원문을 지우지 말고 주석을 덧댄다**(`~~취소선~~` + "→ MM-DD 변경").
  역사를 덮어쓰면 "왜 그랬더라"를 못 찾는다.

### INDEX.md — 세 곳

1. **프로젝트 표의 해당 줄** — 상태·요약 갱신
2. **📢 알림(hook)** — 다른 팀이 알아야 할 것(액션 불필요). 대표가 "~팀에 알려줘"라 했을 때도 여기
3. **⚠️ 미읽 멘션(mention)** — 상대가 **해야 할 일**. 체크박스로. 끝난 건 `[x]` + 취소선 + 결과 한 줄

#### 🚨 INDEX는 **매 세션 통째로 실린다** — 크기가 곧 비용이다 (08-16 신설)
`CLAUDE.md`가 "세션 시작 시 반드시 INDEX.md를 읽어라"고 지시하므로, **이 파일은 모든 세션의 고정 출발 비용**이다.
08-16에 재보니 **188,528자**였고 그중 **알림 하나가 120,659자**(106건 × 평균 1,130자)였다.
알림에 결정 이유·함정·처방까지 다 적혀 있었는데, **그 내용은 이미 정본 노트에 있었다**(표본 3건 전부 2~3곳 중복).

**대표 확정 규칙 — 알림은 「쌓이는 것」이 아니라 「흐르는 것」이다:**
- 📌**최근 15건만 유지.** 넘치면 오래된 것부터 `4_Archive/알림-보관-YYYY-MM-DD.md`로 **옮긴다**(⛔지우지 말 것).
- 📌**한 줄 200자 이내.** 형식 = `- **[이모지] → [대상] (from [팀], 「제목」)** (날짜, 커밋): 핵심 한 문장 → [[정본노트]]`
  「핵심 한 문장」은 *이걸 모르면 헛짓할 것* 하나만. 이유·함정·처방은 **정본 노트가 맡는다.**
- 📌**세는 시점 = ⑤ 보고 직전에 딱 한 번**(디자인팀 제안 08-17). 한 세션이 알림을 여러 건 남길 수 있으니
  **적을 때마다 세지 않는다** — 다 적은 뒤 마무리에서 한 번 세고, 넘치는 만큼 한꺼번에 내린다.
  멘션은 `[x]`로 닫히지만 **알림은 닫는 장치가 없어** 방치하면 무한히 쌓인다.
- 🔁**15는 상한(문지기)이 아니라 창(窓)이다 — 밀어내기다.** 새 알림은 **항상 적는다.**
  적은 뒤 세어서 넘치면 **가장 오래된 것부터 같은 개수만큼** 아카이브로 내린다(예: 15+3=18 → 오래된 3건 이동 → 15).
  ⛔"이미 15건이니 이번 건 생략"은 **오독이다** — 최신 소식이 잘리면 알림의 존재 이유가 사라진다.

#### 🚨 INDEX는 **여러 세션이 동시에 고친다** — 밀어내기 직전에 다시 읽어라 (08-25 실제 사고)
세션 마무리는 세 팀이 **같은 시간대에** 한다. 08-25에 알림 목록을 읽고 몇 분 뒤 밀어내려 했더니
**다른 세션이 이미 오래된 두 건을 아카이브로 옮긴 뒤**였다. 그걸 모르고 **같은 알림을 다른 날짜 파일에 또 넣었다.**

- 📌**밀어내기 직전에 알림 목록을 «다시» 읽는다.** 앞에서 읽어둔 목록으로 편집하지 마라.
- 📌**아카이브는 `4_Archive/알림-보관-<오늘>.md`가 이미 있는지 먼저 본다** — 오늘 다른 세션이 만들어 뒀을 수 있다.
  거기에 **이미 그 항목이 있으면 다시 넣지 않는다** — 존재 확인은 `grep -c`가 아니라 **`grep -q`**로.
  (`grep -c`는 없을 때 **0을 찍으면서 종료코드 1**이라, `&&`로 엮으면 「없음」이 「실패」로 읽혀 뒷 명령이 통째로 안 돈다.)
  🩸🆕**그리고 이 존재 확인을 «셸 루프» 안에서 하지 마라** (09-03 실측). `while IFS= read -r line; do grep …; done < file`은
  **grep이 stdin을 통째로 먹어서 루프가 첫 줄만 돌고 끝난다** — 밀어낸 2건 중 **1건만 아카이브에 적혔다.**
  🪤에러가 안 난다. 「추가: …」가 한 번만 찍히는데 그게 정상처럼 보인다.
  👉**이 단계는 파이썬으로 해라**(읽고-합치고-쓰기가 어차피 필요하다). 그리고 **적은 뒤 「밀어낸 것 전부가 파일에 있나」를 되읽어 대조**하라.
- 🪤**밀어낸 항목과 아카이브에 적은 항목이 «같은 것»인지 확인하라.** 08-25에 스크립트가 민 것과
  내가 손으로 적은 것이 **서로 달랐다**(줄 삽입으로 인덱스가 밀렸다). → 민 줄을 **그대로 출력해** 두고 그걸 붙인다.
- ⛔편집은 **줄 번호가 아니라 「고유 문구」로** 잡는다. 다른 세션이 줄을 넣고 빼는 사이 번호는 바뀐다.
- 🩸**아카이브 파일에 쓸 땐 «덮어쓰기»(`w`·`>`) 금지 — 「읽고-합치고-쓰기」나 `>>`로.** 08-25에 내 스크립트가
  `w` 모드였는데 **상대가 뒤에 붙인 덕에** 살았다. 순서가 반대였으면 상대 2건이 통째로 사라졌고,
  ⭐**지워진 쪽은 아무 신호도 안 남긴다**(파일은 멀쩡히 존재한다).
- 🧮🚨**알림을 세는 «도구»가 무엇을 세는지 확인하라.** 08-25에 `awk '/📢 알림/{f=1}'`로 셌더니 **18건**이 나와
  3건을 밀 뻔했는데, 실제로는 **15건**이었다 — 그 문자열이 파일에 **7번**(헤딩 1 + 멘션 본문 4 + 안내 2) 나와
  **구역이 계속 다시 열렸다.**
  👉**구역은 「첫 등장 인덱스」로 한 번만 열고**(헤딩 `## 📢 알림` 다음 줄 ~ 다음 `## ` 앞), **개수는 그 구역 안의 `^- ` 줄을 센다.**
  ⛔**「📢 알림」이라는 «표시 문자열»을 세지 마라** — 그건 항목 수가 아니라 **그 말이 쓰인 자리 수**(7)다.
  🪤**둘 다 숫자가 멀쩡해 보인다** — 그래서 다시 세기 전엔 못 잡는다.
  🩸🔁**이 줄의 초판이 그 병을 그대로 재발시켰다**(2팀 실측 정정) — *「`grep -c` 말고 `grep -o | wc -l`로」*라고 적었는데
  **둘 다 7이 나온다.** 한 줄에 두 번 나오는 데가 없어서 애초에 차이가 안 생기는 건이었다.
  ⭐**도구를 바꾼 것이지 «세는 대상»을 바꾼 게 아니었다.** 세는 도구를 의심할 땐 **「무엇을 셀 것인가」**를 먼저 정하라 —
  옵션을 갈아 끼우는 건 그다음이다.

⚠️**왜 DM이 있는데도 알림을 남기나** — `send_message` DM은 **지금 켜져 있는 세션**에만 간다.
**내일 새로 여는 세션은 오늘 DM을 못 본다.** 알림의 유일한 고유 가치 = *"내가 안 본 사이에 뭐가 바뀌었나"를 한 곳에서 훑기*.
그건 **최근 것만** 의미가 있어서 15건으로 충분하다. 그 이상은 정본 노트의 일이다.

#### ✂️ 그렇다고 **DM 친 걸 전부 알림에도 적지는 않는다** (대표 08-17)
DM을 보냈다면 **지금 일하는 사람들은 이미 안다.** 알림 줄이 벌어야 할 값은 *내일 새로 오는 세션에게 남는 것*뿐이다.
⭐**판정 한 문장 = 「이게 정본 노트에 이미 적혔나?」**
- 적혔다 → **알림 생략.** 알림 줄은 순수 중복이고, INDEX만 무거워진다(정본을 가리키는 게 알림의 일인데 가리킬 것이 이미 있다).
- 안 적혔다 → 정본 노트에 **먼저 적고**, 알림엔 그리로 가는 한 줄만 남긴다.
⛔"DM 보냈으니 알림도 하나" 같은 반사적 복제 금지 — 그게 105건까지 쌓인 경로다.

## ③ 메모리 갱신 (`~/.claude/projects/-Users-youngduck-Desktop-collab5/memory/`)

**먼저 `MEMORY.md`를 읽고 중복부터 확인한다.** 있으면 새로 만들지 말고 **그 파일을 고친다.**

**메모리에 넣을 것** = *다음 세션이 이걸 모르면 헛발질할 것*:
- 상시 지켜야 할 규칙·함정 (`type: feedback`)
- 외부 환경의 실측 사실 (모델 지형, 서드파티 동작 등)
- 대표의 작업 방식 선호
- ⛔**틀린 게 발견되면 지우거나 고친다** — 낡은 메모리는 없느니만 못하다

**볼트 vs 메모리**: 볼트는 *프로젝트의 기록*, 메모리는 *내가 다음에 안 틀리기 위한 것*.
같은 사실이 양쪽에 있어도 되지만, 메모리는 **한 줄로 압축**하고 정본은 볼트를 가리킨다.

파일 하나당 사실 하나 + `MEMORY.md`에 한 줄 포인터.

## ④ 스킬 갱신 (`.claude/skills/*/SKILL.md`) — ⛔ 건너뛰지 마라 (08-24 신설)

> 대표 지시(08-24): *"이번에는 스킬 업데이트 필요 내용도 꼭 스킬 업데이트 해주고!"*

볼트·메모리를 고치면서 **「다음에 이 작업을 하는 사람이 읽을 문서」는 빼놓기 쉽다.**
볼트는 *프로젝트의 기록*, 메모리는 *내가 안 틀리기 위한 것*, **스킬은 *그 작업의 절차*다.** 셋은 독자가 다르다.

### 무엇이 스킬로 가나
- **작업 절차가 바뀐 것** — 단계가 늘거나 순서가 바뀌었으면 그 스킬의 해당 절
- **그 절차에서 실제로 밟은 지뢰** — 다음 사람이 똑같이 밟을 것
- **대표가 되돌린 판정** — 스킬에 옛 규칙이 남아 있으면 다음 세션이 그걸 읽고 또 틀린다

### 🚨 새 규칙을 얹기 전에 **반대 방향 문장을 먼저 grep 하라**
```bash
grep -rn "<옛 규칙의 핵심어>" .claude/skills/ ~/Desktop/collab5-Obsidian/
```
08-23에 「활동·콜라보 desc는 **최대 3문장**」이 살아 있는 채로 「더 길게 쓰라」를 얹을 뻔했다.
그대로 뒀으면 다음 세션이 **서로 반대인 두 규칙**을 읽는다. 실제로 반대 방향 문장이 **7곳**에서 나왔다.
정본 = memory `prompt-edit-collides-silently`.

### 🔗 스킬은 git으로 공유되고, 심링크는 **1팀 작업트리를 본다** (08-23 실측)

- 그런데 `~/.claude/skills/`의 심링크가 **`~/Desktop/collab5`(1팀 작업트리)**를 가리킨다.

  → 🚨**스킬을 고쳤으면 그 세션 안에서 main까지 병합하고 1팀에 DM한다.** 안 그러면 다음 세션이 옛 버전을 읽는다.
  - 🆕🚨**병합만으로는 «아무도» 못 읽는다 — 1팀이 그 트리를 pull 해야 반영된다** (1팀 실측 09-02).
    심링크가 1팀 트리를 보므로, main에 있어도 **1팀 트리가 낡아 있으면 2팀도 1팀도 옛 파일을 읽는다.**
    ⭐그래서 DM은 통보가 아니라 **「pull 해달라」는 요청**이다. 1팀이 당겼다는 답을 받아야 반영이 끝난 것.
  - 🩸🔁**그리고 이 규칙은 «쓴 다음 날» 한 번 샜다** (09-03 1팀 적발). 하루에 스킬을 네 번 병합했는데
    **#185만 DM을 안 보냈다** — 앞뒤 건(#184·#186)은 보냈다. 중간에 대표가 다른 일을 시켜 흐름이 끊긴 자리였다.
    🪤**원인 = DM을 「방금 고친 것」 기준으로 썼다.** 써야 할 기준은 **「상대가 아직 안 당긴 것」**이다.
    👉**DM 쓰기 전에 한 줄 돌려라** — `git log <상대가 마지막으로 당긴 커밋>..HEAD --name-only -- .claude/skills/`.
    그 목록을 그대로 DM에 붙인다. ⭐**개수를 말로 적지 말고 명령 결과를 붙여라**(09-03에 「SKILL.md 하나」라고 썼는데 실제는 둘이었다).
    📌받는 쪽도 대칭 장치를 쓴다 — 1팀은 pull 후 `--name-only`로 실제 파일을 대조하고 개수가 다르면 되묻기로 했다.
    🔑**그리고 「상대가 마지막으로 당긴 커밋」은 내가 알 수 없다 — 상대가 답신에 적어준다**(1팀 제안 09-03).
    ⭐**프로토콜 = ①내가 `<상대가 알려준 커밋>..HEAD --name-only` 결과를 붙여 pull 요청
    → ②상대가 당긴 뒤 «어디까지 당겼는지 커밋 해시»를 답신 → ③그 해시가 다음 요청의 기준점.**
    이러면 양쪽 다 기억할 게 없다. 🪤앞의 규칙들이 「다음에 이걸 기억하라」였다면 이건 **명령 한 줄이 대신 기억한다**(1팀 평).
    ✅**기준점이 낡아도 괜찮다**(1팀 09-03 실측). 상대가 답신을 준 뒤 «자기» 커밋을 병합하면서 내 것까지 당겨가는 일이 있다 —
    그러면 내 기준점은 낡고 범위가 **넓게** 잡힌다. 넓은 쪽은 안전하다(이미 있는 걸 또 당기면 no-op).
    ⛔위험한 건 반대 방향(좁게 잡기)인데 이 구조에선 안 생긴다. 📌**받는 쪽이 「이미 갖고 있다」고 답하면 그걸로 닫는다** —
    「어? 이미 있네, 뭐가 잘못됐나?」로 멈추지 마라.
  - 🩸🚨**그리고 «내 트리에서» 고쳐라.** 09-02에 2팀이 `~/.claude/skills/`(심링크) 경로로 편집해
    **1팀 작업트리 파일을 직접 바꿔 놓았다** — 1팀 `git status`에 남의 변경이 뜬다.
    ⭐**심링크 경로로 스킬을 쓰지 마라. 항상 `<내 작업트리>/.claude/skills/…`로 연다.**
- ⚠️**다른 팀이 그 스킬을 만지는 중일 수 있다.** 고치기 전 `git fetch` → 병합, 고친 뒤 겹침 DM.

- [ ] 반대 방향 문장을 **전수로 훑었나**
- [ ] 상대 팀에 **알렸나**
